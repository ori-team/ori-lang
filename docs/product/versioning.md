# Versioning model

Ori currently uses **0.3.8** as the canonical public project version.

This document prevents different version concepts from being mixed in status pages, specifications, package metadata, runtime metadata, and release notes.

## Version classes

| Version | Current value | Meaning |
|---|---:|---|
| Project version | `0.3.8` | Public version used for the compiler, language distribution, and current documentation |
| Cargo workspace version | `0.3.8` | Version declared in `compiler/Cargo.toml` and inherited by workspace crates |
| Language surface | S3, current in `0.3.8` | Accepted syntax and semantic surface; S3 was introduced earlier but is not itself the current version number |
| Native ABI version | `ori-native-abi-1` | Compatibility tag for layouts, runtime symbols, mangling, and staged runtime metadata |
| Project manifest schema | `manifest = 1` | Schema of `ori.proj` and related project metadata |
| Package/lock formats | Independently documented | Formats may evolve under the stability policy |
| Documentation/book version | Artifact-specific | Must state which project version its examples target |

## Canonical rule

The phrase **current version** means `0.3.8` unless the text explicitly names another version class.

Correct examples:

- “Ori 0.3.8 uses the S3 language surface.”
- “The S3 cut was introduced in 0.3.0.”
- “This feature was added in 0.3.7 and is present in 0.3.8.”
- “The native ABI remains `ori-native-abi-1`.”

Incorrect examples:

- presenting `0.3.0`, `0.3.1`, or `0.3.2` as the current project version;
- treating the ABI tag as interchangeable with the compiler version;
- using “0.3.x” where an exact current version is required;
- copying a historical milestone table into a current status page.

## Pre-1.0 compatibility

Ori follows semantic-versioning intent while remaining pre-1.0:

- patch releases may include fixes and compatible additive behavior;
- a deliberately incompatible public language change requires an explicit compatibility decision and a suitable version transition;
- incompatible native runtime layouts or symbol contracts require a new `ori-native-abi-N` tag;
- user-visible removals require release notes and, where practical, migration support;
- experimental behavior may change only when it is clearly marked experimental in the normative stability document.

## Sources of truth

- Workspace version: `compiler/Cargo.toml`
- User-visible release history: `CHANGELOG.md`
- Current status: `docs/product/status.md`
- Stability contract: `docs/spec/18-stability-and-compatibility.md`
- ABI contract: `docs/spec/19-abi.md`
- Runtime package metadata: `runtime/<target>/runtime-link.json`

Generated or staged metadata must agree with the Cargo workspace version and ABI contract.

## Version update procedure

A version change must update, as applicable:

1. `compiler/Cargo.toml` and workspace crate metadata;
2. lockfile metadata generated by Cargo;
3. current product status;
4. root README files;
5. runtime-link metadata and package builders;
6. installer and updater expectations;
7. changelog release heading;
8. docs and book banners that claim an exact current version;
9. CI checks that validate package metadata;
10. release checksums and artifact names.

Do not update historical statements such as “introduced in 0.3.0” unless the historical statement itself is wrong.

## Automated validation target

Documentation CI should eventually enforce:

- the current version is read from `compiler/Cargo.toml`;
- active status documents do not claim a different current version;
- runtime metadata contains the expected project and ABI versions;
- historical version references use an allowed context such as “introduced”, “released”, or a changelog heading;
- release artifact names use the release version consistently.

## 1.0 policy

A 1.0 release is a maturity decision, not a calendar target. It should require:

- a stable and documented language contract;
- a sustained compatibility window;
- a reliable native ABI and runtime distribution model;
- a coherent standard library;
- reproducible releases across supported targets;
- complete migration and deprecation policies;
- strong conformance, security, and performance evidence;
- documentation that is navigable and synchronized with implementation.

Self-hosting may contribute to maturity, but it is not the sole requirement for 1.0.
